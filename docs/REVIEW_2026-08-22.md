# Review — theme + settings + voice + vision work (2026-08-22)

Scope reviewed: the dark/light theme work, the cross-platform settings store,
the Android wake-word/recording services, the desktop voice path, and the
Images/Vision feature (web + desktop + Android). Findings are prioritized.

---

## Bugs (behavior is wrong)

### B1. `/vision/analyze` skips analysis of uploaded images when the screen is unchanged
- **Where:** `app/tools/vision_analyzer.py` (`analyze_screen_image`) → `ScreenCaptureTool.capture_screen_delta()`.
- **What:** `analyze_screen_image` calls `capture_screen_delta()`, which captures a **fresh screen frame** and compares its hash to the previous screen. If the screen hasn't changed, it returns `screen_changed=False` and skips the LLM analysis **entirely** — even when the caller asked to analyze an *uploaded image file*, not the screen.
- **Impact:** the web "Choose image…" / desktop "Choose image…" / Android "Choose image" flows can silently return "Desktop screen state is unchanged…" instead of analyzing the chosen image. The delta-dedup only makes sense for the screen-observation path (`/vision/capture-and-analyze`), not for `/vision/analyze` on an arbitrary image.
- **Fix:** split the dedup from analysis — only run `capture_screen_delta` on the capture-and-analyze path, or add a flag to skip the delta check when analyzing a user-supplied image.

### B2. Web Settings posts to the backend on every keystroke / slider tick
- **Where:** `frontend/src/app/routes/VoiceSettingsPage.tsx` — the wake-word `onChange` and voice-speed slider `onChange` each call `updateSharedSettings(...)` immediately.
- **What:** typing "hi android" fires ~10 POSTs; dragging the speed slider fires dozens. No debounce, so requests race and can persist out of order.
- **Fix:** debounce (or save on blur/commit) before calling `updateSharedSettings`.

### B3. Android app theme and backend theme are two sources of truth
- **Where:** `MainActivity.kt` applies `theme` from local DataStore (`settings.theme`); `SettingsScreen` displays/edits the **backend** theme (`viewModel.theme`).
- **What:** on a fresh install with backend `theme=light`, the app still renders dark (DataStore default) until the user opens Settings and hits Save. Editing theme on web/desktop doesn't change the Android app's rendered theme.
- **Fix:** hydrate the app theme from the backend on startup (fall back to DataStore), and keep both in sync on save.

### B4. Desktop theme is read from local QSettings, not the backend
- **Where:** `desktop/app.py` — `apply_theme(self.settings.get("theme") or "dark")` at startup.
- **What:** desktop pushes `theme` to the backend on Save, but never pulls it back. Setting theme on web/Android does not re-theme the desktop on next launch. The "backend-driven" claim is one-way.
- **Fix:** hydrate `DesktopSettings.theme` from `get_shared_settings()` at startup (short timeout) before `apply_theme`.

## Gaps / incompletes

### G1. Persisted voice settings are not applied when the pipeline starts fresh
- **Where:** `backend/voice/service.py` `start()` constructs `VoicePipeline(...)` without passing `voice`/`tts_speed`; `update_settings` early-returns `if not self.pipeline`.
- **What:** set voice speed to 1.5 (or a non-default Piper voice) in Settings, then start voice → the pipeline runs at defaults (speed 1.0, default voice) because nothing reads the stored values at start. Live `update_settings` only applies while the pipeline is already running.
- **Fix:** read `get_settings()` in `start()` and pass `voice`/`tts_speed` into `VoicePipeline`.

### G2. Several settings are stored but never consumed
- `noise_suppression`, `response_delay`, and `voice_enabled` have **no backend consumer** (grep found none). They round-trip through the store and all three UIs but do nothing.
- The web's `noiseSuppression` in `useVoice.ts` is a hardcoded `true` unrelated to the store.
- **Fix:** either wire them (noise gate in VAD, delay before TTS, gate voice start on `voice_enabled`) or drop them from the UI to avoid implying behavior that doesn't exist.

### G3. PC wake word can't honor arbitrary custom phrases
- **Where:** `backend/voice/service.py` `update_settings` maps wake words through a fixed `wake_word_map` (`hey_arena`/`hey_lumi`/`hey_mycroft`/`alexa` → Picovoice models); anything else falls back to `"hey_jarvis"`.
- **What:** a custom wake word saved in Settings does not actually gate the PC-side pipeline. (Android's SpeechRecognizer accepts arbitrary text, so only Android honors custom phrases.)
- **Fix:** surface the supported wake-word set in the UI, or document that PC-side keywords are limited to the installed Picovoice models.

### G4. Desktop theme switch requires restart
- Colors are baked into QSS at widget-construction time, so in-session switching is not applied (the UI says "theme applies on next launch"). Web and Android re-skin instantly.
- **Fix (optional):** re-apply a global app stylesheet + re-style uniform controls via `findChildren` on theme change, or accept restart-only and keep the note.

### G5. Web Images page leaks object URLs
- `URL.createObjectURL(file)` for the local preview is never revoked (`frontend/src/app/routes/ImagesPage.tsx`).

### G6. "Vision" is OCR + LLM summarization, not image understanding
- `analyze_screen_image` sends OCR text (not the image) to the LLM. No VLM is run (RX 580 can't hold one). This is a documented hardware limit, but the feature is effectively "OCR + text summarization", not true visual analysis.

### G7. Android parity gaps
- No "system" theme option (web has dark/light/system).
- Wake-word re-arm uses `startService` for a foreground-typed service, so if the app is backgrounded the wake word won't resume (caught + logged, no user feedback). Inherent Android restriction.

## Not verifiable in this sandbox (honest)
- **Android build** — no Android SDK; Kotlin reviewed by hand only (compiles not confirmed).
- **Qt runtime** — no display; `py_compile` passes but the window wasn't launched.
- **Live Piper selection / voice pipeline** — backend can't be run here, so the `_apply_settings_live` wiring is untested end-to-end.

---

## Code-quality debt (not bugs)
- `desktop/app.py` is ~1800 lines, monolithic (theme, settings, chat, vision, tools, voice all in one file). Worth splitting into `desktop/pages/` + `desktop/theme.py`.
- Four theme stores with partial sync: web localStorage, desktop QSettings, Android DataStore, backend `settings.json`. The backend is nominally the source of truth but each client also keeps a local copy that can drift (B3/B4).

---

## Recommended order
1. **B1** (vision analysis correctness) — directly breaks a feature just shipped.
2. **G1** (voice speed/voice not applied at start) — the headline "option 1: Piper everywhere" is undermined if a saved voice/speed is ignored.
3. **B2** (debounce settings POSTs) — small, removes backend spam.
4. **B3/B4** (theme hydration) — makes "backend-driven" actually true.
5. **G2/G3** — either implement or remove the dead/cosmetic settings.
